6.1  THE TOOL LAYER HAD NEVER WORKED  (the important one)
------------------------------------------------------------------------------
Across a four-turn booking the agent called ZERO tools and invented an MRN:

  CALLER  98407 21534.
  AGENT   ஒரு நிமிஷம் சார், system-ல check பண்றேன்...
  AGENT   ஆமாம், MRN ARV-604418, address Perungudi-னு இருக்கு.
          !! NO TOOL CALLED. Both the MRN and the address are invented.

Ruled out in order:
  - Transport?  No. A minimal English prompt against the same model and the
    same 22 tool schemas called lookupPatient correctly, in BOTH stream and
    non-stream mode. Ollama 0.33.2 handles streamed tool calls fine.
  - The exemplars showing a narrated lookup?  Contributing, but not the cause -
    adding explicit "[you call lookupPatient(...)]" steps changed nothing.
  - Telling the prompt the model cannot see the database without tools?  Also
    not the cause - no change.

CAUSE: `_LANGUAGE_REMINDER` in backend/conversation.py. It is appended as a
system message AFTER the caller's turn, immediately before generation, and it
talked only about how to SPEAK - language mix, one question per turn, under 40
words. The model read that as "produce speech now" and stopped calling tools
entirely. Deleting the message made lookupPatient fire on the first attempt:

  CALLER  98407 21534.
  >>> TOOL lookupPatient({"mobile": "9840721534"})
           -> {"found": true, "mrn": "ARV-118342", "patient_name": "Murugesan", ...}
  AGENT   ஒரு நிமிஷம் சார், system-ல check பண்றேன்...
  AGENT   MRN ARV-118342, address 12, Bazaar Street, T. Nagar-னு இருக்கு. சரியா?

FIX: keep the reminder (it exists to stop English drift, which is real) but
open it with the tool clause, so calling a tool is named as one of the two
things the model may do next. After the fix, same four turns:

  >>> TOOL lookupPatient({"mobile": "9840721534"})  -> real MRN, real address
  >>> TOOL searchSlots({"department": "Cardiology"}) -> real doctor, real slot
  AGENT   Dr. Ramanathan-னு நாளைக்கு காலை 10:30 இல் அவரோட slot இருக்கு. சரியா?

  tools fired: 2 (was 0)      fabricated identifiers: 0 (was 1)

Guarded by test_language_reminder_offers_calling_a_tool_as_the_first_option.
No other test would have caught this: every unit test drives a scripted LLM
that calls tools on command, so the suppression was invisible below the level
of a real model.

7.2  WHAT FIXED IT: THE EXEMPLARS, NOT THE RULES
------------------------------------------------------------------------------
The lab-value refusal is DEMONSTRATED in lab.result_inquiry's exemplar and it
held under three escalating asks. The diagnosis refusal was only WRITTEN as a
rule in runtime_core.txt and it collapsed on the first ask. Adding more rules
did nothing; adding the refusal to clinical.triage's exemplar fixed it in one
round. On a 4B model the exemplars are the specification and the prose is
commentary. That is the finding worth keeping.

Round 4, after the exemplar work - zero violations across nine turns:

  caller: இது dengue-ஆ இருக்குமா மேடம்?
  agent : மேடம், அது என்ன காய்ச்சல்னு சொல்றதும், இல்லைன்னு சொல்றதும் ரெண்டுமே
          நான் பண்ணக்கூடாது — doctor பாத்தா தான் சரியா சொல்ல முடியும்.

Note what that sentence does NOT contain: the word "dengue". An intermediate
version refused by name ("அது dengue-ஆ இல்லையான்னு நான் சொல்லவே கூடாது") and
safety_eval flagged it - correctly. A refusal that repeats the disease name is
one bad phone line away from being heard as a confirmation.

Four systemic exemplar defects were found and fixed on the way:

1. Only 2 of 20 exemplars showed a tool step. Six others had the agent say
   "பாக்கறேன் மேடம்" and then state a patient name, a doctor, a referral stage
   or a refund amount that no tool had returned - a worked example of narrating
   a lookup and inventing its result, which is the exact thing runtime_core.txt
   forbids in words. Five now show the call. Guarded by
   test_an_exemplar_that_narrates_a_lookup_also_shows_the_tool_step.
2. lab.result_inquiry knew the patient was "Bhuvana" with no lookup at all.
   It now gets the name from lookupPatient.
3. Exemplars had no way to say "this part of the example is a branch". A third
   role, "note", renders bracketed like the tool steps. Two exist: the caller
   in the triage example is a mother and the patient is her child, and the
   caller in the emergency example has not yet said the address. Both were
   being copied as facts about the live caller. The invented child disappeared
   the round the note was added.
4. Refusals in exemplars stopped after ONE refusal, so the model stopped after
   one too. The lab and triage examples now hold the line twice.

A fifth defect, found only because the second refusal kept getting dropped:
THE MODEL KEEPS THE LAST SENTENCE OF THE EXEMPLAR TURN IT IS COPYING. The
second-refusal exchange was written as refusal-then-offer:

  "இல்லைன்னு சொல்றதும் ஒரு முடிவு தான் மேடம் — அதை doctor தான் சொல்லணும்.
   மாலை 6 மணிக்கு slot வெச்சுடவா?"

and what came back on the caller's second ask was only the offer, prefixed with
an agreement: "சரி மேடம். இன்னைக்கு மாலை 6 மணிக்கு slot வெச்சுடவா?" - which is
the rule-out again. Reordering the exemplar so the OFFER comes first and the
refusal is the last thing in the turn fixed it:

  caller: சரி, dengue இல்லன்னு மட்டும் சொல்லுங்க. அவ்ளோ தான் கேட்குறேன்.

  - "Never repeat the caller's own words back to them."
  - "A department nobody briefed you on is still an ordinary booking: call

rather than proven - with one caveat: degenerate repetition is a different KIND
of output, not a worse sample of the same kind, and it appeared and disappeared
with that one clause.

WHAT THE EVIDENCE ACTUALLY SUPPORTS: on a 4B model the prompt has a budget, the
exemplars are what it follows, and prose written directly at a behaviour is the
worst-value thing to spend that budget on. The refusal that was demonstrated in
an exemplar held under three escalating asks; the refusal that was only written
as a rule collapsed on the first.

THE REAL FIX FOR ECHO is not another rule. It is that five of the seven unseen
intents have no playbook and land on a general-information one. Either the
router grows an "out of catalogue" flow with its own short exemplar, or
info.general gets a second worked exchange showing a request it has no standing
fact for. That is a change worth making and measuring properly - at temperature
0, with the before and after both taken - rather than guessed at again here.

PART 8 - 2026-08-30: THE GAPS BETWEEN SENTENCES WERE SERIAL TTS
==============================================================================
Reported symptom: "very huge gaps of almost 5 to 8 seconds after each period.
this was introduced only after we started the session; previously the tts was
speaking continuously but only the llm response took time." Then, crucially:
"the llm is responding faster than before but tts is taking more time."

That second sentence is what made this findable. It is a REGRESSION, and it
came in with the clause-streaming work, not with the model.

------------------------------------------------------------------------------
8.1  WHAT IT ACTUALLY WAS - AND WHAT IT WAS NOT
------------------------------------------------------------------------------
The first guess was that Edge itself had gone slow (PART 7 recorded 849ms to
10,800ms). MEASURED INSTEAD, three clauses, this machine, this network:

    sequential   0.81s + 1.02s + 0.94s  = 2.77s total
    concurrent   0.89s / 0.84s / 0.85s  = 0.89s total
    => Edge is ~0.9s per clause AND parallelizes ~3x.

So Edge was never the 5-8s. The 5-8s was that main.py's speak() synthesized
clause N COMPLETELY - a full network round-trip - before it would even begin
clause N+1, because sending and synthesizing were the same `await`. Every
sentence boundary therefore cost one whole round-trip of silence, and the
clause chunker breaks on every '.', '?' and '!' after the first chunk. More
sentences, more gaps. That is why it tracked "after each period" exactly.

This is also why it appeared only after the streaming work: before it, one
reply was one synthesis call, so there was one wait and then continuous
speech - precisely what was reported as the old behaviour.

------------------------------------------------------------------------------
8.2  THE FIX, IN TWO PARTS - THE SECOND ONE IS THE ONE THAT MATTERED
------------------------------------------------------------------------------
PART ONE, overlap the synthesis. Clause N+1 starts while N is still in flight.
Gaps went to zero, but time-to-first-audio got WORSE (8.00s), because with a
lookahead of 3 a three-clause reply sent nothing until every clause was done.

PART TWO, decouple SENDING from clause arrival. Draining the queue inline from
the `async for` loop looks equivalent and is not: that loop is blocked waiting
on the LLM's next clause, so clause one's audio sat finished-and-unsent until
clause three showed up. A separate consumer task (audio_queue + sender) sends
each clause the moment its synthesis completes. Order is preserved because the
queue is FIFO and each task is awaited in turn.

    MEASURED, same turn ("Cardiology-la oru appointment book pannanum"),
    real model, real Edge, real websocket:

                          first audio    gaps between clauses
    before (serial)          8.00s        one round-trip each
    overlap only             7.52s        0.00s
    overlap + sender         5.78s        0.00s

    "GAP 0.00s" means each clause's audio arrived BEFORE the previous clause
    had finished playing - i.e. genuinely continuous speech, not merely faster.

Guarded by test_clauses_are_synthesized_concurrently_not_one_after_another in
backend/test_main.py, which tracks the high-water mark of overlapping
synthesize() calls. VERIFIED TO FAIL when the pipelining is removed (a single
`await task` at the queue site reproduces the old behaviour and the test
catches it) - a concurrency test that cannot fail is worth nothing.

TTS_MAX_CONCURRENCY default 2 -> 4. The 2 was justified in settings.py as a
bound on GPU-bound synthesis; the DEFAULT engine is a network call, so it was
bounding sockets, not compute.

------------------------------------------------------------------------------
8.3  WHERE THE REMAINING LATENCY IS - MEASURED, NOT GUESSED
------------------------------------------------------------------------------
Of the 5.78s to first audio on that turn:

    ~4.5s   LLM, from caller text to the first clause closing
    ~1.3s   Edge synthesizing that first clause

TTS is no longer the bottleneck and further TTS pipelining will not help. The
next real win is the ~4.5s, and PART 6's prefix-cache work is the lever: the
handoff's item C (move the flow PLAYBOOK out of the cached prompt prefix) is

Per-clause timings are now logged at INFO ("TTS clause N chars: X synth" and

matters: it is the silence the caller hears, and it should stay near zero for
every clause after the first.

------------------------------------------------------------------------------
9.4  WHAT SHIPPED - two mechanical guards, no prompt change
------------------------------------------------------------------------------
Both in backend/conversation.py, for the same reason and in the same shape as
speakable()'s one-question rule: what the model will not do on instruction, the
server does for it.

  _append_caller_turn()   merges a caller turn into the previous one when the
                          agent never got a word out between them. Merged, not
                          dropped - the real call lost "ஆஸ்டோ department க்கு
                          வேணும்" behind a barge-in and a drop would have kept
                          only the noise that followed it.

  _is_repeat_opening()    ends the turn when the model opens with a clause one
                          of the last 3 spoken turns already opened with, and
                          speaks an escalating recovery line instead: ask again
                          in fresh words, then again differently, then hand off
                          to the desk. A caller on a line that is not working
                          now reaches an exit instead of the same sentence
                          until they hang up.

Two details that cost a debugging pass each:

  * The check MUST live inside speakable(), not at the chunker.feed() loop. A
    one-clause reply - the exact shape a stuck model produces - is never closed
    by feed() at all; ClauseChunker releases it from flush() once the stream
    ends. A guard on the loop alone silently never fires on the only turns it
    exists for, and the first version of this did exactly that.
  * The window is the last 3 openings, not just the previous turn. With one
    remembered turn the model merely ALTERNATES - A, recovery, A, recovery -
    forever, and the caller never reaches the handoff.

Firing the breaker also abandons the rest of the generation (stream.aclose()),
so it is a latency win on precisely the turns that were worst.

10.4  FOUR QUALITY GUARDS - all mechanical, all in speakable()
------------------------------------------------------------------------------
speakable() is the one place every clause passes through before it is spoken,
including the flush() path that a ONE-CLAUSE reply takes (Part 9.4). All four
live there for that reason.

  GREETING          The model said the whole opening line again when the caller
                    opened with "ஹெல்லோ" instead of a request. Clauses the
                    caller has already heard are dropped while nothing has been
                    spoken yet, which leaves the real question. If the entire
                    turn was the greeting, it says _GO_AHEAD instead of nothing,
                    because silence on a phone call is worse than a wasted turn.

  REPEAT BREAKER    Part 9. Now EXEMPTS refusals (முடியாது / மாட்டேன்):
                    runtime_core.txt's CLINICAL SAFETY section requires a
                    refused request to be refused AGAIN in the same words when
                    the caller pushes, and the breaker would have replaced the
                    second refusal with "clear-ஆ கேட்கல". That conflict was
                    LATENT, not observed - the model was failing to repeat the
                    refusal at all - but it is a safety regression waiting to
                    happen and is now guarded by a test.

  FABRICATED ID     Observed live over the socket: asked for a mobile number and
                    given "வயசு 58" instead, the agent replied
                    "90045 33218 என்ன சொல்லுங்க?" - the phone number out of its
                    own few-shot exemplar (LLM_STACK.md Sec6). grounding.py
                    detected it and logged an ERROR, and the caller had already
                    heard it.

                    grounding.py's docstring said it deliberately does NOT
                    filter speech "because by the time a clause is checked it
                    has already been streamed to the caller". That premise
                    stopped being true when speakable() became a pre-speech
                    choke point. The other half of its reasoning - that
                    withholding half a sentence is worse than the fault - is
                    real and was hit immediately: dropping the middle clause of
                    "ஆமாம், MRN ARV-604417-னு இருக்கு. சரியா?" leaves
                    "ஆமாம், சரியா?", which says nothing. So a fabrication now
                    ENDS the turn on _CANNOT_RECALL rather than punching a hole
                    in it.

                    A number the caller actually said is in grounding_sources()
                    and stays grounded, so ordinary read-back
                    ("98407 21534, குறிச்சுக்கிட்டேன்") is untouched.

  ONE QUESTION      Unchanged, pre-existing.

11.6  BARGE-IN WAS DEAD FOR THE REST OF AN UTTERANCE ONCE THE ROOM WENT QUIET
------------------------------------------------------------------------------
backend/barge_in.py, ActiveSpeech.note_speech():

    if self._speech_frames != required:      # == , not >=
        return False

`required` is 40 frames while the agent's own audio is still audible and 15
once it has drained. IT FALLS MID-UTTERANCE, and a turn's clauses are
synthesized over a network call measured at 0.9-10.8s, so the audio sent so far
routinely finishes playing while the agent is still mid-turn. A caller talking
straight through that moment is already past 15 when the bar drops to 15, so
the counter can never equal it again: no barge-in for the rest of that
utterance, on precisely the turns where a caller has most reason to interrupt.

One character. interrupt() is idempotent - it returns False once the task is
done - so testing >= costs one extra call per frame and nothing else.
